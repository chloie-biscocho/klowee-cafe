# 009 — Media goes to Supabase Storage, through the API

## Context

The menu, events and the site's hero and story sections all need photos. The
owners will upload them from the admin app on a phone or a laptop. The database
already lives on Supabase, which includes an S3-backed object store, so the
storage question is really two questions: which bucket, and *who talks to it*.

The tempting answer is "the browser talks to it directly". Supabase's client
library is built for that: the browser gets an anon key, storage policies decide
what it may write, and the API never sees the bytes. It saves a hop.

## Decision

**Supabase Storage, one public bucket named `media`, written only by the API.**

- **The API is the only holder of the key.** `Supabase:ServiceRoleKey` and
  `Supabase:Url` are bound to `Common/SupabaseOptions.cs` and read in
  `Services/SupabaseStorageService.cs`. The key lives in user-secrets locally
  and an environment variable in production. It never reaches a browser. In
  Development the app refuses to start without both, so the failure is at
  startup rather than on the first upload.
- **Plain `HttpClient` over the Storage REST API**, from `IHttpClientFactory` —
  no Supabase SDK, no S3 SDK. Three routes are the whole surface:
  `POST /storage/v1/object/{bucket}/{path}`,
  `DELETE /storage/v1/object/{bucket}/{path}`, and the public read URL
  `/storage/v1/object/public/{bucket}/{path}`.
- **`IStorageService` is the seam.** `UploadService` owns the rules and knows
  nothing about Supabase; `SupabaseStorageService` is transport and knows nothing
  about the rules. Tests substitute a fake and exercise the rules without a
  network call.
- **The rules, in `Services/UploadService.cs`:** JPEG, PNG or WebP only; 5 MB
  maximum; the first bytes must actually be that format; the folder must be
  `menu`, `events` or `site`; the stored key is
  `{folder}/{yyyy}/{MM}/{guid}.{ext}`, generated by the server, never the
  caller's file name. Deletes are refused unless the path starts with one of the
  three folders.
- **The bucket is public for reads.** These are marketing photos on a public
  website; signed URLs would add expiry handling to every rendered `<img>` for
  no benefit.

## Why not upload straight from the browser

- **One key, in one process.** A browser upload needs a key in the browser. The
  anon key plus storage policies can be made safe, but the safety then lives in
  policy SQL that nobody on this team has written before, and a mistake there is
  silent and public. The service role key in a server process is one secret in
  one place with no policies to get wrong.
- **One place to validate.** Content type, size and magic bytes are checked
  server-side, where the check cannot be skipped. A browser-side check is a
  courtesy, not a control: anything that can call the storage endpoint can lie
  about what it is sending.
- **The path is the server's to choose.** Generated keys mean no collisions, no
  path traversal, no user-supplied file names on a public URL, and a layout
  (`folder/year/month`) that stays browsable as it grows.
- **The API already authenticates the caller.** `POST /api/uploads` sits behind
  the same JWT as every other admin endpoint. No second authorisation story.

The cost is one extra hop and the API buffering the file. At 5 MB and two
uploaders, that is not a real cost. If it ever becomes one, the answer is signed
upload URLs issued *by the API* — which keeps the validation and the key exactly
where they are.

## Consequences

- Uploading is one endpoint with one error shape, like everything else.
- Swapping Supabase Storage for anything else is one class.
- Trade-off: bytes pass through the API, so it needs enough memory and a request
  size ceiling. Kestrel's default 30 MB body limit is the outer backstop; the
  5 MB rule rejects anything smaller with a readable 400.
- Trade-off: deleting an entity does not delete its photos. `coverPhotoUrl` and
  `event_photos.url` are strings, not foreign keys, so orphaned objects
  accumulate. Acceptable while media is small; a sweep that lists the bucket and
  compares against referenced URLs is the eventual answer.
